- Karpenter, HPA, 캐싱 전략을 적용해 EC2 인스턴스 2~3대만으로 대규모 트래픽을 안정적으로 처리하고 인프라 비용을 최적화했습니다.

## EKS 프로젝트 트러블슈팅: DB 커넥션 초과 문제
- 문제: product, user API에 트래픽이 몰릴 때 애플리케이션(Pod)들이 만든 커넥션 총합이 DB의 max_connections를 초과해, 신규 커넥션이 거부되며 요청이 실패했습니다.
- 원인: Pod 오토스케일링 시 "Pod 수 × 커넥션 풀 크기"가 DB의 max_connections를 넘는 구조였습니다. 커넥션이 애플리케이션마다 독립적으로 관리되어 재사용되지 못했고, 트래픽 급증 구간에서 한도를 초과했습니다.
- 해결 1 - RDS Proxy 도입: 다수의 애플리케이션 커넥션을 소수의 DB 커넥션으로 멀티플렉싱(재사용)했습니다. 앱 쪽 커넥션 총합이 max_connections를 넘어도 Proxy가 큐잉·재사용으로 흡수해 요청 실패를 막았습니다.
- 해결 2 - 인덱스 최적화: 조회 빈도가 높은 컬럼에 인덱스를 설정해 쿼리 속도를 개선했습니다. 커넥션 점유 시간이 줄어 동시 커넥션 수요 자체가 감소했습니다.

## 포트폴리오 RAG 챗봇 chat.sjhan.com (2026)
- 역할: 개인 프로젝트
- 기술: FastAPI, Gemini API(답변 생성·임베딩), PostgreSQL + pgvector, React(TypeScript), k3s, Jenkins, GHCR, VictoriaMetrics, Grafana
- 내용: 지금 보고 계신 사이트입니다. 한승재의 자기소개 문서를 섹션 단위로 나눠 검색한 뒤, 관련 내용만 근거로 Gemini가 답변합니다.
- 포인트: 문서를 섹션 단위로 임베딩해 pgvector에 저장하고, 질문과 코사인 유사도가 높은 섹션을 찾아 답변 근거로 씁니다. 답변마다 참고한 문서 출처를 함께 보여줍니다.
- 배포: main 브랜치에 push하면 GitHub webhook으로 클러스터 안의 Jenkins가 바뀐 부분만 이미지로 빌드해 GHCR에 올리고 k3s에 배포합니다. 새 버전이 5분 안에 준비되지 않으면 이전 버전으로 자동으로 되돌리고, 자기소개 문서가 바뀌면 적재 Job도 다시 실행합니다.

## 포트폴리오 RAG 챗봇 트러블슈팅: 첫 자동 배포 때 이미지를 받지 못한 문제
- 문제: Jenkins 파이프라인으로 처음 자동 배포했을 때 이미지 빌드와 GHCR 업로드는 성공했지만, 새 API 파드가 이미지를 받지 못해 ImagePullBackOff 상태에 머물렀고 배포 단계가 실패했습니다.
- 원인: GHCR 패키지는 처음 올릴 때 Private으로 만들어지는데, k3s 노드는 인증 없이 이미지를 받도록 구성돼 있어 GHCR이 401 Unauthorized로 요청을 거부했습니다.
- 해결 1 - 자동 롤백: 새 파드가 5분 안에 준비되지 않자 파이프라인이 rollout undo로 이전 버전을 되살리고 빌드를 실패로 표시했습니다.
- 해결 2 - 이미지 공개 전환: API 키 같은 시크릿은 이미지에 넣지 않고 Sealed Secrets로 실행할 때 주입하므로, 이미지 패키지 2개를 Public으로 바꿨습니다. 이 절차는 k3s README에 정리했습니다.
- 결과: 배포가 실패한 동안에도 기존 파드가 계속 응답해 서비스에는 영향이 없었고, 다시 빌드하자 이미지 배포와 문서 적재까지 자동으로 끝났습니다.
